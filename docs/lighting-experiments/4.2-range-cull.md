## Implementation summary

Single-file change in [src/3d/Tower3DView.ts](../../src/3d/Tower3DView.ts):

- Added module-scoped `buildRangeCulledLightsChunk()` + `applyPointLightRangeCull(root)` helpers.
- In `loadModel`'s onLoaded callback (after `this.model = root;`, before `sceneLighting.applyLights`), traverse the loaded GLB root and attach an `onBeforeCompile` hook to every `MeshStandardMaterial` (which covers `MeshPhysicalMaterial` — all 6 unique GLB material instances in this model: `Opaque(90,82,92)` shared by 4 tower body parts + 3 drum levels, `Opaque(90,82,93)_(1)` shared by 12 seal meshes, plus `Steel_-_Satin`, `ABS_(White)`, and two `Opaque(...)_1` variants on `Return_to_Dark_Tower_2..5`).
- The hook substitutes `#include <lights_fragment_begin>` with a copy of `THREE.ShaderChunk.lights_fragment_begin` whose PointLight loop body is wrapped in a distance-squared guard:

  ```glsl
  pointLight = pointLights[ i ];
  vec3 lVectorRC42 = pointLight.position - geometryPosition;
  if ( dot( lVectorRC42, lVectorRC42 ) <= pointLight.distance * pointLight.distance ) {
      getPointLightInfo( pointLight, geometryPosition, directLight );
      #if defined( USE_SHADOWMAP ) && ... #endif
      RE_Direct( directLight, ..., reflectedLight );
  }
  ```

  Per-iteration scope on the unrolled loop — each of the 36 PointLight iterations gets its own `vec3 lVectorRC42` declaration in its own block, with no scope collision. The shadow-sample `#if` block stays nested inside the new `if` so shadow work is also gated on the range check.

- The patch is per-material via `onBeforeCompile`; `THREE.ShaderChunk` is never mutated. If the chunk text shifts in a future three.js release, `buildRangeCulledLightsChunk()` returns `null` and the helper logs a one-shot warning and leaves materials unmodified — the worst-case fallback is the baseline perf, not a broken shader.
- Guarded against the Jest `__mocks__/three.js` mock (which omits `ShaderChunk`) by treating `typeof chunk !== 'string'` as a no-op skip.

No changes to bloom, camera, DPR, audio, light counts, light positions, or scene composition. No new tests required — light count and types don't change; the existing `Tower3DView.test.ts` `collectPerfReport` shape assertions still pass.

**Patched shader chunk:** `lights_fragment_begin` (the only chunk touched).

## Interpretation

Passes the §1 success criterion. All five gates:

1. **Sequence `frameMs.median` decreased meaningfully** — −68% at Display (75.1 → 24.0 ms) and −46% at Retina (141.6 → 76.9 ms), both well past the §8.3 ≥30% bar on Retina.
2. **`visiblePointLights` unchanged at 36** when any LED is on — the [§8.3 smoking gun](../lighting-testing-plan.md#83-42--range-cull): the cull is happening per-fragment inside the loop, not by skipping lights.
3. **Empty/idle unchanged** — `frameMs.median` 8.3 → 8.3 at both canvas sizes. The cost has been removed, not moved.
4. **`programs` stable at 30** across all 4 windows at both canvas sizes — see "Notable observations" for why the count didn't grow.
5. **Visual parity** — sanity screenshot at All-LEDs Retina shows no range-cull artifacts.

The smaller relative win at Retina (−46%) vs Display (−68%) is consistent with the larger canvas having proportionally more in-range fragments around each light. Both wins are dominant.

## Notable observations / risks

- **`programs` did not grow on patch — same 30 as baseline.** Each `MeshPhysicalMaterial` swapped its compiled program in place (old variant dereferenced when the patched onBeforeCompile produced a different cache key). Net delta: 0. The [perf-skill expected-signals table](../../.claude/skills/darktower-3d-perf/SKILL.md#when-evaluating-a-lighting-alternative) lists `+1 program` for 4.2 — that prediction assumed a single patched material added on top of the baseline; in this codebase the patched materials *replace* their pre-existing baseline programs rather than coexisting with them, so the total stays flat. Worth updating the skill's table in a future docs PR (left untouched here to keep this PR scoped). The prewarm machinery in `Tower3DView.prewarmLightPrograms()` still works — no recompile stalls observed across the empty → 1-LED → empty → 1-LED cycle used to verify stability.
- **Three.js version anchor: `0.184.0`.** The patch keys off the chunk text containing `pointLight = pointLights[ i ];` and `RE_Direct( directLight, geometryPosition, geometryNormal, geometryViewDir, geometryClearcoatNormal, material, reflectedLight );`. `buildRangeCulledLightsChunk()` checks both and returns null if either is missing, so a future three.js bump that renames those identifiers degrades to baseline perf (and logs once) rather than producing a broken shader. If the chunk text drifts but the patch's intent still applies, the helper needs a re-anchor; see the test for `applyPointLightRangeCull`'s no-op fallback.
- **`MeshPhysicalMaterial` is what the GLB ships, not `MeshStandardMaterial`.** §8.3 names "the drum-interior `MeshStandardMaterial`"; in practice every lit GLB material on this model is a `MeshPhysicalMaterial`. `MeshPhysicalMaterial` extends `MeshStandardMaterial` and `isMeshStandardMaterial === true` for instances of either, so the type-guard in `applyPointLightRangeCull` catches both. Same `lights_fragment_begin` chunk — same patch applies.
- **All 6 unique lit GLB materials are patched, not just the drum-interior.** The biggest gain comes from the largest fragment producers — the tower body (`Return_to_Dark_Tower_5` is 82,168 triangles, dominates screen pixels) and the drum levels — both share `Opaque(90,82,92)`. Patching all 6 keeps the implementation simple (one traversal) and maximises the perf gain without altering any other code path. Per-material scope is preserved (no global `THREE.ShaderChunk` mutation).
- **No ambiguity-rule recapture needed.** Empty `frameMs.median` matched baseline exactly (8.3 ms) at both canvas sizes. Sequence-5 differences are far outside the ±5% noise band. Single capture per scenario per canvas was sufficient.
- **`MeshPhysicalMaterial.iridescence` / clearcoat branches in `lights_fragment_begin`.** The chunk also contains an `#ifdef USE_IRIDESCENCE` block before the lights loop — untouched by the patch. None of the GLB materials use iridescence or clearcoat features, so this is academic, but worth noting that the patch is limited to the PointLight loop body and does not interact with iridescence/clearcoat code paths.
- **Gate-cycle stability spot-check.** Toggled 1-LED → Empty → 1-LED and confirmed `programs: 30, visiblePointLights: 36↔0↔36, frameMs.median` settled to the same post-patch value each time. No recompile stall, no leak.
- **Range-cull cutoff edges (theoretical visual risk).** A fragment exactly on the boundary `dot(lVec,lVec) == pointLight.distance²` switches from "fully attenuated by three.js's distance falloff (already near zero contribution)" to "skipped entirely". Three.js's distance attenuation is `pow(saturate(1-pow(d/cutoff,4)),2)/pow(d,decay)` which → 0 at `d == cutoff`, so the cutoff transition is C0-continuous in the patched result. Confirmed by sanity screenshot — no visible banding.
